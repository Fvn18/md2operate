# 1. 深度总结

## 1.1 一页纸结论

**方向是对的，但这份文档现在还不能拿去实施——它把「愿景」「契约」「实现」「计划」写在了同一个编号体系里，其中 3 条被当成事实的承重假设，已经被本机实测否证或高度可疑。**

具体判断（按对实施的影响排序）：

1. **最大的一处：`.fmt` 预编译被写了三遍**（SLO 表、§3.1、阶段二交付），而它在本项目的引擎组合下**实测失败**（`xelatex: fatal: Could not undump`；`%&fmt` 与 `-fmt=` 冲突）。这是全篇唯一「读者照做必然翻车」的地方。
2. **`≥500 tasks/s` 没有量纲**：`task` / `job` / `document` / `page` 全文混用。按本项目实测耗时反推，500 doc/s 的 PDF 口径需要 **1,650~3,000 个并发渲染槽位**——这不是数字错，是**这句话现在无法被证伪，也无法被排期**。
3. **`P95 ≤ 50 ms` 的归因错了**：现状预览在**客户端 Web Worker 内**完成，实测逐键 p50 **24.4 ms** / p95 **25.6 ms**（E2 §5.1）。把公式渲染搬到「分布式公式热缓存」是在这条链路上**净增一个 RTT 与一次调度**，不是优化。文档需要先回答「P0 通道跑在哪一侧」。
4. **「零磁盘接触」与文档自身的 1,200 DPI 能力互相矛盾**：300 DPI 长图实测 2953×16719（解码后 ≈ 197 MB），同样内容按 1,200 DPI 是 ≈ 3.16 GB；而 §3.2 写「64 MB 缓冲阈值，超出溢出 tmpfs」——那么**绝大多数导出都会溢出**，"零磁盘"是名义上的。且 TeX 路线**必须**有可写输出目录（`.aux/.log/.out`），literal 零磁盘不可能。
5. **通篇没有「正确性」SLO**，只有可用性/延迟/吞吐。对一个渲染中台，**最危险的故障是"内容变了却返回旧产物"**——本项目上一轮刚修过同类缺陷（缓存签名漏了 11 个输出相关选项 → 发陈旧产物）。这类故障不会体现在 99.95% 里。
6. **零信任章节漏了真正在前台的那个沙箱逃逸面**：Chromium 路线。仓库现状是 `--no-sandbox`（E3 `server/chrome.mjs:217-241`）、markdown 解析 `html: true`（E3 `shared/markdown.mjs:605`）、渲染页由内置 HTTP 注册表以**同源**方式加载。文档把零信任全押在 TeX 上，而 TeX 路线在现状里反而更收敛（集中构造参数、无用户可控命令行）。
7. **`PDF/UA 自动补齐` 与 `零频域空间隐写` 是两条无法验收的需求**（前者不会自动达成；后者的术语本身不成立）。它们必须改成「per-route 合规矩阵 + 可测验收」与「三种水印分层 + 鲁棒性边界」，否则会变成永远做不完的欠债。

一句话：**这份文档该保留的是"要建分布式渲染中台"这个判断；该重写的是"度量契约"和"承重假设的验证状态"。**

## 1.4 现状锚点（供「靶子校准」，避免把已有资产当缺口重写）

> 本项目上一轮最大的教训就是**靶子打偏**：把 `command -v` 内建探测当成"每次几十毫秒的开销"。同样的错误在这份企业级文档里又出现了一次——它把下列**已经存在且已被实测**的东西当成了待建能力。

| 已具备（不要重写） | 位置/证据 |
|:--|:--|
| 同构渲染不变量：预览逐块拼接 == 导出整篇 HTML（3598 KB 逐字节一致）；增量 == 全量（1087 KB） | E2 §2.1 |
| 块级增量协议 v2：位置优先匹配 + 身份继承 + 行区间补丁（`order/blocks/ranges/removed`），有 `verifyDelta()` 自校验 | E3 `shared/preview-engine.mjs`、`web/src/lib/preview-client.ts:199` |
| 缓存签名（客户端版 CAS）：`signature()` 覆盖 33 个字段，命中即跳过重编 | E3 `md2pdf:821-831, 920-926` |
| 栅格化 5 级回退链：`pdftoppm → pdftocairo → gs → mutool → sips`，每级判 `$?` 与产物大小；sips 明示「72dpi 放大，属降级」 | E3 `server/raster.mjs:25-200` |
| 取消语义：CDP 无取消消息 → 杀浏览器实例（实测 158 ms、0 孤儿进程） | E1、E2 §2 |
| 微秒级链路探针：命令→pandoc 只拉起 1 次、缓存命中零 pandoc、<15 ms / <20 ms 断言 | E1 `scripts/verify-kernel.mjs`（22 项） |
| 12 个 `verify*.mjs`（1 主控 + 11 子套件），其中 `verify:preview` 的"逐字节相同"是全项目最硬护栏 | E3 `package.json`、E2 §7 |
| 已修的真实 cache-bug：`--colorlinks/--template/--page` 等 **11 个输出相关选项**曾未进签名 → 发陈旧产物 | E1 |

**含义**：企业级文档应新增一节 **§0.3「现状基线（已达成）」**，把这些写成"不变量"而不是"路线图任务"；否则路线图会重复劳动，AI 也会把已完成的资产当成缺口。

# 3. 修改意见（REV-01 … REV-26）

每条格式：**位置 → 问题 → 建议改法 → 证据 → 验收 → 严重度**。

## 3.1 P0：会误导实施、必须改

### REV-01　`.fmt` 内存转储从「事实」降级为「待验证假设」`AH-1`

- **位置**：§1 SLO 表（"TeX 预编译内存转储"）／§3.1「利用前文所规划的预加载内存转储（`.fmt` 文件）」／§5 阶段二交付项。
- **问题**：三处承重，且已被实测否证：`xelatex: fatal: Could not undump`，`%&fmt` 魔数与 `-fmt=` 冲突（E1）。按文档字面实施 = 返工。
- **建议改法**：
  1. 全文三处统一改为：`（假设 AH-1，未验证）预编译格式转储可能降低冷启开销；本组合（xelatex + 原生 CJK 字体）实测失败，须在目标平台复测。`
  2. 新增 **AH-1 实验卡**（模板见下），并给出**替代路径**而非只留一个洞：
     - 减重路线：测量 preamble 逐包成本（`\RequirePackage` 排序、`ctex` 与 `fontspec` 的真实占比），先把"每包必付"的固定成本压掉；
     - 进程路线：**已经实测**的固定开销优先治理（每次 `pandoc --version` 31.2 ms，连"源文件未变直接跳过"那次也付；E1），这类改动不改输出、风险低；
     - 引擎路线：仅在「允许输出变化」的明确授权下才评估 luatex/Typst，且必须附带版面差异报告。
  3. **反例保留**：把"为什么不能靠 `%&` 魔数"的实测报错原文写进文档，防止后来者重试。
- **验收**：文档中不再出现任何"已可达到 0.4 s"的断言；`AH-1` 卡片含：环境矩阵、实验步骤、成功判据、失败后的替代路径。
- **严重度**：P0（阻塞）

### REV-02　`≥500 tasks/s` 重写为「参考负载 × 每 vCPU 产能」

- **位置**：§1 SLO 表「高吞吐吞吐量」。
- **问题**：`task` / `job` / `document` / `page` 混用；无 workload 画像；无峰值/持续之分。按实测反推：PDF 3.3–6.0 s/doc、PNG(300DPI 长图) 1.0–1.9 s/doc（E2 §5.1），500 doc/s ⇒ **1,650–3,000 个并发渲染槽位**（PDF 口径）／**500–950 槽位**（PNG 口径）。这不是"做不到"，而是**必须写成可排期、可验收的形式**。
- **建议改法**：以参考负载定义吞吐，并给出统一量纲。
  - `W1`：A4 双页纯文本 PDF（≤5 KB 源）— 目标 p95 单文档耗时 ___ s
  - `W2`：20 页 / 100 公式 / 含表格与代码块 PDF
  - `W3`：300 DPI 长图 PNG（≥2 MB）＋ `W4`：1,200 DPI 单页
  - 指标：`renders/s`（**已完成**）与 `docs/s` 分开；持续（≥30 min）与突发（≤60 s）分开
  - 产能表达：`docs/s/vCPU`（例：`W1 ≈ 0.2 docs/s/vCPU`，则由 500 docs/s 反推所需 vCPU 与成本）
- **验收**：任意读者能据文档算出"要多少钱、多少节点"；压测脚本可复现同一数字（附录 A-3）。
- **严重度**：P0（阻塞）

### REV-03　先钉死 P0 通道的**执行位置**，再定 P95

- **位置**：§1 SLO「网页实时预览渲染延迟（P95）≤ 50 ms」+ 机制列「AST 增量解析 + 分布式公式热缓存」。
- **问题**：现状预览**完全在客户端**：解析 + KaTeX + 分块在 Web Worker，主线程只贴 DOM；实测逐键 p50 24.4 ms、p95 25.6 ms（E2 §5.1）。把公式搬到"分布式热缓存"= 在这条链路上加一次网络 RTT + 一次调度，**方向相反**。另：现状是**块级**增量（token 流分块 + 身份继承），不是"AST 增量解析"（措辞不准）。
- **建议改法**：
  1. 新增小节 **§2.1.0「渲染执行位置（必须单列）」**，明确三档：
     - `L0 客户端内`（现状能力，厚度最薄、延迟最低）→ 用于 P0 预览；
     - `L1 就近服务端`（同一 AZ 内部）→ 用于薄客户端/协同场景；
     - `L2 分布式渲染`（跨节点）→ 仅用于 P1/P2。
  2. SLO 改为可测口径：`输入事件 → 下一帧呈现` 的 p95（并注明测量方法）；若走 L1，须把 RTT 计入预算并给出实测差值。
  3. 术语改为「块级增量 + 身份继承」，与实现对齐（E3 `shared/preview-engine.mjs`）。
- **验收**：文档中"公式热缓存"不再出现在 P0 的**机制**列（除非给出跨机实测数据支撑）；P95 定义含测量方法与执行位置。
- **严重度**：P0（阻塞）

### REV-04　「零磁盘接触」重述为可测性质，并与自身 DPI 能力对齐

- **位置**：§3.2 全节；§5 阶段一交付项「无临时文件流式管线」。
- **问题**：① TeX 路线**必须**有可写输出目录（`.aux/.log/.out`），literal 零磁盘不可能；② 64 MB 缓冲阈值与 1,200 DPI 能力冲突——实测 300 DPI 长图 2953×16719，解码缓冲 ≈ 197 MB；同为 1,200 DPI ⇒ ≈ 3.16 GB（1,200 DPI 单页 8325×2013 ⇒ 解码 ≈ 67 MB）；③ 现状尚存 5 处 `mktemp`（stdin 落盘、错误尾捕获、`-j` 任务目录、watch 目录、自举），其中只有部分在热路径上。
- **建议改法**：把要求改为三条**可测性质**，并按路线给表：
  - `P-a` 不落**持久**盘：所有中间产物仅存在于内存或 tmpfs；
  - `P-b` tmpfs 用量**计入** cgroup 内存限额（否则 OOM 依旧）；
  - `P-c` 峰值内存上界给公式：`peak ≈ Σ(bitmap_W×H×4B) + 编码缓冲 + 引擎常驻`，并对超阈场景给**分块/条带渲染**策略而非"溢出到 tmpfs"。
  - 附「可纯内存 / 必须 tmpfs / 必须落盘」三列 × 各路线（预览 / Chromium-PDF / PNG / TeX-PDF / docx）的对照表。
  - 注明移除每个 `mktemp` 时**不能破坏**什么：错误尾诊断（现状成功路径也会 grep LaTeX 错误）、`-j` 的完成信道（现状用 FIFO + 结果文件）、stdin 输入支持。
- **验收**：文稿中"零磁盘"字样被替换为 `P-a/P-b/P-c`；给出每路线的 tmpfs 用量估算与实测峰值。
- **严重度**：P0（阻塞）

### REV-05　新增「数据治理与保密」章节（全文缺失）

- **位置**：新增 §2.6。
- **问题**：多租户文档中台处理的是客户商业机密，但文档全篇没有一处提到：产物与源码的静态加密、保留期、删除请求（DSR）、日志脱敏、审计留痕。**现状已经有一个真实泄露面**：引擎输出被中继进任务日志（E3 `server/render.mjs:626-633`），正文片段/路径可能落进日志与 SSE 流。
- **建议改法**：新增章节，至少覆盖：① 正文与产物加密（at-rest/in-transit）；② 日志脱敏规则（默认不落正文，只落哈希与统计）；③ 保留期与删除 SLA（含 CAS 中的副本与 CDN 边缘缓存失效）；④ 审计事件与不可否认；⑤ 数据驻留（region pinning，与"多活"冲突时以谁为准）。
- **验收**：能回答"客户要求删除某文档的全部产物，多久、如何证明"。
- **严重度**：P0（阻塞）

## 3.2 P1：过度承诺，需改成可验收形式

### REV-06　PDF/UA 不写「自动补齐」，写 per-route 合规矩阵

- **问题**：真正的 PDF/UA-1 需要标签结构、阅读顺序、公式/图片的 alt 文本、字体 ToUnicode CMap、并通过校验器；LaTeX 路线要 tagpdf 类宏包（实验性），Chromium 路线只能靠 `printToPDF` 的 tagged PDF 能力起步，二者都不"自动"。
- **建议改法**：给「路线 × PDF/UA 状态」矩阵（`不支持 / 部分（缺 math alt） / 通过`），并规定验收 = **veraPDF PDF/UA-1 profile 0 失败**；数学与图片的 alt 生成单独立项（明确是否依赖 AI 描述、是否人工审阅）。
- **验收**：矩阵中每格有可跑的命令或明确"不支持"。
- **严重度**：P1

### REV-07　水印需求拆成三层，删掉「零频域空间隐写」

- **问题**：「零频域」不是术语（空间域/频域/扩频才是）；且"隐形"在 PDF 里通常靠不可见文本/OCG 层实现，**不是**隐写，可被无损移除；"打印→扫描后仍可提取"是另一个数量级的工程，必须显式声明鲁棒性边界。
- **建议改法**：分三条独立需求，各自有验收：
  - `W-a 溯源元数据`（XMP/文档 ID/操作人工号）：保证"可读"，**声明可被移除**，属弱保证；
  - `W-b 可见水印`（平铺/页脚）：验收=渲染后可见性断言；
  - `W-c 隐写水印`：先写**鲁棒性目标**（如"矢量 PDF 内、不压缩重排 → 提取成功率 ≥ 99%；截图/OCR/重排版后不保证"），再选算法（扩频/DCT+纠错码），验收含误码率与假阳性率。
- **验收**：三条各自有实验；删除"零频域""不可见盲水印"字样。
- **严重度**：P1

### REV-08　SLO 表补「正确性 / 新鲜度」，指标与 OTel 规范化

- **问题**：99.95% 只度量"有没有响应"。对渲染服务，最危险的是**陈旧产物**（本项目上一轮真实故障：11 个输出相关选项未进缓存签名 → 内容变了返回旧产物）与**静默降级**（DPI 被降、引擎被换而调用方不知情）。另外，OTel 五段指标里 `engine_init_duration_ms` 之类在沙箱内根本没有生产者，且高基数标签（文档哈希）不能进指标。
- **建议改法**：
  - SLO 表新增两行：`陈旧产物率 = 0`（以"输入指纹 → 产物指纹"的对账任务度量）、`静默降级率 = 0`（任何降级必须出现在响应头/manifest）。
  - 「不可用」定义（哪些端点、哪些返回码计入）+ 错误预算策略（何时冻结发布）。
  - 指标规范：高基数进 trace、低基数进 metric；span 边界由编排层持有；沙箱内以"文件级证据 + 单一父 span"代替伪精确子 span；删除"亚毫秒级"这类分辨率承诺（改述为采样分辨率）。
- **验收**：SLO 表每一行都有"如何度量/在哪看/谁负责"。
- **严重度**：P1

### REV-09　背压：P0 靠**预留**而不是靠 429；「利用率」必须定义

- **建议改法**：① 定义信号（worker 槽位占用率 / 队列时延 / 引擎池饱和度，三者取阈值组合，而不是笼统的 85%）；② P0 走**预留配额**（独立池 + 最小保有容量），429 只作用于 P1/P2；③ `Retry-After` + 抖动（避免惊群）；④ 429 响应体必须带机器可读的 `retry_at`、`queue_class`、`quota_scope`。
- **验收**：给一张"信号 → 动作"表；有压测证明 P0 在 P1/P2 洪峰下 p95 不劣化。
- **严重度**：P1

### REV-10　50,000 队列：把持久化语义、幂等与保留期写清

- **建议改法**：写明 ① 队列持久化（Kafka/Streams）⇒ **至少一次**投递 ⇒ 渲染任务必须幂等（与 CAS 天然协同，明写出来）；② payload 与日志保留（现状 `MAX_JOBS=200`、`MAX_LOGS=5000`，E3 `server/jobs.mjs:14-15`）；③ 内存/存储记账：50k × (元数据 + 日志尾) ≈ ___ MB；④ 每秒新增/消费速率与积压清的放时间上界（Little's Law 示例）。
- **验收**：给出"积压 50k 时，P1 任务最长等待时间"的算式。
- **严重度**：P1

## 3.3 P2：架构决策

### REV-11　CAS Key 必须「来自单一事实来源」并配漂移测试

- **问题**：文档的 `Key = SHA256(DocAST + ThemeCSS + FontsVersion + EnginePreset)` 覆盖不足，且历史上本项目因签名漏项出过事故（E1：`--colorlinks/--template/--page` 等 11 项未进签名）。漏项 ⇒ 陈旧产物，是这类系统最隐蔽的故障。
- **建议改法**：
  1. Key 的输入集合必须**由构建渲染命令的同一处代码生成**（现状是 `signature()`，E3 `md2pdf:821-831`），新增选项时**编译期/测试期**强制同步；
  2. 补进 Key 的维度（现文档缺失）：`date/TZ`（`\today`、时间戳元数据）、`locale/连字符规则`、引擎**二进制版本**（xelatex/pandoc/gs 版本）、**字体文件内容哈希**（不只是 `FontsVersion` 标签）、平台标识（字体回退与栅格器选择会变）、**路由器版本**、**降级后实际使用的引擎**（见 REV-12）；
  3. 新增**漂移测试**：枚举参数清单，任一参数存在但未进 Key ⇒ 测试失败（这正是"漏 11 项"的防复现装置）。
- **验收**：给出 Key 字段全表（字段 → 来源 → 变更影响）；漂移测试进 CI。
- **严重度**：P2（但漂移测试是 P1 级收益）

### REV-12　降级后 `requested ≠ executed`：实际引擎必须入 Key 与响应

- **建议改法**：产物 manifest 记录 `requested_engine` / `executed_engine` / `downgrades[]`；Cache Key 用 **executed**；响应头机器可读（`X-MDP-Route`、`X-MDP-Effective-DPI`、`X-MDP-Downgrades`）。同时统一措辞："DPI 降采样说明写在响应头"要写成**结构化**字段，而不是"说明文字"。
- **验收**：同一次请求在降级/未降级下，Key 与产物可区分且可追溯。
- **严重度**：P2

### REV-13　自适应路由器：纯函数 + 版本化

- **建议改法**：路由决策必须是 `(doc_features, theme, presets, router_version)` 的**纯函数**，输出写入 manifest 并进 Key；`router_version` 变更视为**破坏性变更**（失效全量缓存），须走发布流程。反之，任何"学习式/基于运行时拥塞"的路由都必须禁入 Key 之外的分支。
- **验收**：给定同一输入，任一节点任一时刻得到同一路线。
- **严重度**：P2

### REV-14　「无状态 Worker」与「常驻引擎」的边界写清

- **建议改法**：明确区分三层：**会话无状态**（可任意调度，现状√）／**进程常驻**（预热池、daemon，允许但不承载状态）／**状态亲和**（仅在必要处，如需要热缓存的分片）。并给出池的实测数字作为设计输入：冷启 200–400 ms（文档自带）vs 取消=杀实例 158 ms（E1）——**取消语义决定了池的回收粒度**。
- **验收**：一句话能回答"节点重启后，正在跑的 500 个任务怎么办"。
- **严重度**：P2

### REV-15　取消语义 × 多租户爆炸半径（文档完全没写）

- **问题**：现状取消 = 杀掉整个浏览器实例（E1/E2：158 ms、0 孤儿）——在单机单人下是最优解；**在共享池里会波及他人**。文档没有定义取消的粒度。
- **建议改法**：明确取消域与代价矩阵：`context 级`（快、隔离好、资源回收慢）/ `进程级`（现状，会丢弃同实例其他上下文）/ `任务级协作式`（最贵、最精确）。给出三者在 P0/P1/P2 的取舍与"取消后实例是否可复用"的判定。
- **验收**：有一个测试能证明"取消 A 的任务不会影响 B 的任务"（多租户前提）。
- **严重度**：P2

### REV-16　零信任章节必须覆盖 **Chromium 路线**（现状最前台的逃逸面）

- **问题**：文档把隔离全押在 TeX 上，而现状里 Chromium 路线是：`--no-sandbox`（E3 `server/chrome.mjs:217-241`）、markdown 允许原始 HTML（`html: true`，E3 `shared/markdown.mjs:605`）、渲染页由内置 HTTP 注册表以**同源**方式加载、HTTP 服务默认**无 token** 且回环监听（E3 `server/server.mjs:84,144`）。在有原始 HTML + 同源 + 本地 API 的组合下，文档级注入就是一个真实的攻击面（本地单人工具下可接受，多租户下不可接受）。
- **建议改法**：新增「Chromium 路径威胁模型」并使规则对称：
  1. 是否继续允许 `html:true`？给出**策略开关**与默认值（多租户默认关闭或过消毒）；
  2. 沙箱内浏览器是否仍 `--no-sandbox`？给出替代（seccomp + 只读 rootfs + 无网络 + 独立用户名空间）；
  3. 渲染页必须与 API **不同源**（独立 origin/端口 + 不携带凭据 + CSP 禁止外联）；
  4. 出站必须是**默认拒绝**（含 `file:`、`chrome://`、内网段、云元数据地址）；
  5. 资源耗尽（`\def` 递归、深嵌套、超大图片、压缩炸弹）与**配额**（CPU/内存/墙钟/进程数/输出字节上限）。
- **验收**：给出一张"攻击面 × 现状 × 目标"表，且每条有对应测试（含一条注入用例）。
- **严重度**：P2（若确认多租户，升为 P0）

### REV-17　TeX 白名单的技术校正

- **问题**：「完全禁用 shell-escape」不够精确；`texmf.cnf` 只能约束**搜索路径**；"只允许内置安全宏包"没有可执行定义。且 `pandoc` 自身读文件（`include-in-header`、`resource-path`、`--metadata-file`），文档未提。
- **建议改法**：写成可执行的旋钮清单：
  - `shell_escape=f` / 调用侧显式 `-no-shell-escape`；禁用 `\write18` 的一切变体；
  - `openin_any=p`、`openout_any=p`（paranoid）：禁绝对路径与 `..`；
  - 只挂载**受控 TEXMF 树**（白名单目录）替代"宏包白名单"幻想；`TEXMFVAR/TEXMFHOME/TEXMFOUTPUT` 指向隔离的可写目录；
  - 若评估 LuaTeX：`os.execute` / `io.open` 必须视为红线（Lua 侧沙箱弱），默认排除；
  - `pandoc` 参数面集中构造（现状已如此，作为**不变量**写明：用户不可注入任意 CLI 参数）。
- **验收**：给出一条"恶意文档 → 期望被拒/无副作用"的用例集并跑通。
- **严重度**：P2

### REV-18　缓存一致性等级与 CDN 交付语义

- **建议改法**：① 明写不变量"**同 Key ⇒ 同字节**"，并给出唯一的破坏来源清单（引擎/字体/平台/时间依赖，见 REV-11）；② 跨平台/跨字体版本 ⇒ Key 带平台维度，命中率按平台分开统计；③ CDN 链接给生命周期：签名 URL、TTL、失效（含"内容删除后边缘缓存如何失效"）、租户隔离；④ 把"零运算成本"改为"不触发渲染"，并把命中率与陈旧率**分开**监控。
- **验收**：可回答"同一文档在两台不同节点上命中同一 Key 时，产物是否允许不一样"——文档必须给出唯一答案。
- **严重度**：P2

### REV-19　把「同构不变量」升级为**企业契约**（文档最大的漏项）

- **问题**：现状最硬的资产是一条可证伪的不变量：**预览逐块拼接 == 导出整篇 HTML（逐字节，3598 KB）**、**增量 == 全量（1087 KB）**（E2 §2.1）。企业级文档里这条不变量消失了，取而代之的是"分布式缓存 + 多引擎"——而多引擎恰恰是它的最大威胁（同一文档在不同引擎/降级路径下**必然**不同版面）。
- **建议改法**：新增 **§2.0「不变量（Invariants）」**，逐条给出可执行断言与 CI 门禁：
  - `INV-1` 预览 vs 导出同构（允许差异的**白名单**：仅页边距/分页相关）
  - `INV-2` 增量结果 == 全量结果（逐字节）
  - `INV-3` 缓存命中产物 == 未命中产物（逐字节）
  - `INV-4` 降级必须可见（manifest + 响应头）
  - `INV-5` 取消不留孤儿进程/临时资源
  - `INV-6` 预检与执行一致（本项目 P0 缺陷正是这条缺席：预检 409 而实际可渲染，E2 §4.1）
- **验收**：6 条都有脚本；CI 任一失败则阶段不允许推进。
- **严重度**：P2（作为文档结构，收益极高）

### REV-20　CRDT → 编译输入必须确定性

- **建议改法**：明确"CRDT 状态序列化必须是**确定性**的（同一状态集 ⇒ 同一 markdown 输入）"，否则产物不可复现、不可归档、CAS 失效；并声明合并语义（同位置并发编辑的判定规则）与"无手动合并"而非"无冲突"；协同模块建议**独立立项**（现文档用一句话承载一个季度）。
- **验收**：给定同一 CRDT 状态的两个副本，编译输入逐字节一致。
- **严重度**：P2

### REV-22　给每条需求加 ID 与验收字段（供 AI 使用的前提）

- **建议改法**：全篇需求编号 `REQ-<域>-<三位>`（域：`SCHED/CACHE/SEC/SRE/ASSET/COMPAT`），并强制三字段：

```markdown
#### REQ-CACHE-004　块级内容寻址复用
- 需求：对语义分块计算内容指纹；未变化的分块不得触发重新渲染。
- 依据：CL-12 / E4
- 验收：同一文档二次编译，渲染器调用次数 ≤ 变化块数 + 1；断言脚本 `verify:kernel` 内。
- 度量：二次编译耗时 / 首编耗时 ≤ ___%
- 关联不变量：INV-2 / INV-3
- 状态：已实现（客户端） / 待实现（服务端）
```

- **理由**：没有稳定 ID，AI 无法生成测试、无法做覆盖矩阵，人也无法判断"这条到底做完没有"。**这就是"供 AI 使用"的落地形式**。
- **验收**：随机抽 10 条需求，都能追到一条断言或一个明确"未实现"标记。

### REV-23　体裁拆分：SRS / ADR / Roadmap / Runbook 分开

- **问题**：现在同一编号体系里混装了愿景（§1）、契约（§1 表）、设计（§3）、计划（§5）。任何一处改动都会牵动全文，且评审时无法区分"这条是承诺还是设想"。

- **验收**：`srs.md` 里不再出现实现细节与工期；`roadmap.md` 不再出现需求定义。

### REV-24　新增「现状基线」章节，避免重复劳动与误判缺口

### REV-25　路线图重排：加「阶段 0」，并给每阶段退出准则

- **问题**：现四阶段没有前置平台、没有角色/工期、没有退出准则、没有风险；且阶段一直接跳到 gVisor 沙箱，**跳过最贵的实验**（`.fmt`、平台矩阵、基准 harness）。
- **建议改法**：新增阶段 0（2~4 周，只做实验与冻结，不做产品化）：
  - `S0-1` 平台矩阵与可复现镜像（工具+字体+浏览器版本全部锁定，版本号进 manifest）
  - `S0-2` 基准 harness：W1–W4 参考负载 + 单机产能基线（现有 `scripts/bench.mjs` 扩展）

- **验收**：每阶段都有一句"如何判定完成"，且不依赖主观判断。
- **严重度**：P3（但决定项目是否做得成）

## 3.5 术语表（建议直接补进文档 §0.1）

| 术语 | 定义（须唯一） |
|:--|:--|
| **task** | 一次 API 请求（可能产生多个产物路线） |
| **render** | 一次「输入指纹 → 产物」的渲染执行 |
| **artifact** | 单个产物文件（PDF/PNG/TEX/DOCX），有独立指纹 |
| **job** | 队列中的可调度单元（1 job ≥ 0 render，可全缓存命中） |
| **slot** | 一个并发渲染槽位（≈1 有效 vCPU + 内存配额） |
| **P0/P1/P2** | 只与**延迟目标**和**调度池**绑定，不与文档类型绑定 |
| **Key** | CAS 键；定义 = 完整输入指纹（含引擎/字体/平台/路由版本） |
| **executed_engine** | 实际使用的引擎（降级后 ≠ requested_engine） |
| **陈旧产物** | Key 相同但输入已变；或输入相同但产物与当前引擎不符 |

**禁用词**：彻底、完美、零成本、永远、毫秒级、亚毫秒级、自动补齐、智能判定（除非紧跟可测阈值）。
